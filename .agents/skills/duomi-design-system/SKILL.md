# DUOMI Design System V2.0

## 0. 使用范围与执行优先级
- 适用于 DUOMI 办公系统、项目工作台、项目管理、工序计划、派单、巡检、验收、客户反馈、售后、业主端小程序。
- 优先级：用户当前明确要求 > 已确认真实业务/安全约束 > 本 DUOMI 规范 > 通用 TasteSkill 建议。不得用任何 Skill 代替真实代码与数据核对。
- 先阅读本文件，再按需阅读 `.agents/skills/design-taste-frontend/SKILL.md`；如果无法读取，直说，不得声称已使用。
- DUOMI 项目覆盖 TasteSkill 默认配置：`DESIGN_VARIANCE=6`、`MOTION_INTENSITY=1`、`VISUAL_DENSITY=5`。不制作磁吸、循环漂浮、闪烁、玻璃折射等非必要动效。
- Caveman 只控制 AI 沟通措辞，不控制页面设计，也不能删减复杂任务的交付信息。

## 1. 品牌视觉：先保留正确的品牌，再创造新界面
- 品牌色依据**正式 DUOMI 橙色 Logo**和用户确认的《多米装饰-宣传册(1).pptx》。宣传册是品牌视觉语言基准，而不是要求办公 UI 做成海报。
- 必须使用真实 Logo 资产；不得用纯文本“DUOMI”、自行绘制的假 Logo 或通用图标替代正式品牌标识。资产缺失时明确标注“Logo 待提供”，不能伪造。
- 真实品牌橙的 HEX/RGB 只能从用户提供的正式 Logo / 已批准设计资源中提取并记录来源；未取得时使用暂定设计 token，明确标注“非最终品牌色”，不把截图估色宣称为官方色。
- 配色原则：白色导航及页面表面、明亮暖白主背景、深灰正文、品牌橙用于重要主操作与少量状态强调。统一暖中性色，拒绝灰冷色与暖灰随意混搭。
- 不使用黑色/深灰大面积侧栏、黑色主按钮、霓虹渐变、橙金营销海报、大片照片和装饰性阴影。深灰可以用于文字、细线、信息对比，但不占据整个导航背景。
- 品牌视觉：大面积干净留白、清晰大字号标题、细灰分隔线、克制的橙色线条/角标、规整的模块秩序。优先无阴影，必要时用 1px 边界线区分。
- 原版 DUOMI 界面中有效的品牌配色与辨识度应保留；允许全面重做控件、信息组织与布局节奏。不是把旧界面换色，也不是随意颠覆品牌。
- Apple / Tesla 仅借鉴克制、细节品质与信息秩序，不照搬具体界面，不转为泛 SaaS 或暗色工业控制台。

## 2. 设计 token 与桌面尺度
- 统一定义并复用：`--duomi-brand`、`--duomi-brand-soft`、`--duomi-canvas`、`--duomi-surface`、`--duomi-text`、`--duomi-text-muted`、`--duomi-border`、`--duomi-focus`。品牌 token 的最终值必须有真实资源依据。
- 桌面设计基准：1440px 视口作对照预览；导航侧栏建议约 208–232px，顶部工具栏约 56–72px，内容区横向内边距 24–32px。根据实际业务密度调整，不强行套用。
- 正文字号一般 14–16px；主要页标题建议 24–28px；分区标题建议 16–20px；辅助说明不小于 12px。中文优先系统无衬线字体，避免长时间办公的小字密排。
- 使用一致的 4/8px 间距体系。表格行高建议 52–64px；表单及按钮常用高度 36–44px，点击目标应清晰。标题、标签、按钮、控件对齐统一。
- 选中导航：浅橙背景/左侧橙色指示条与清晰文字，而非大面积深色底。一级、二级导航有明确层级；实际菜单与权限保持原有边界。
- 状态标签须以文字+颜色共同识别；橙色不承担所有状态。高对比文字、键盘焦点、加载、空状态、错误、禁用状态必须可辨认。
- 移动小程序沿用色彩与组件语义，但使用真实移动端布局，不直接缩小桌面表格。

## 3. 工程管理感来自任务与信息，不来自装饰图案
- 工作台优先组织“今天需要行动的事”：真实的在管项目、待办、审核、异常、最近进度；仅展示源码/API 确认可提供的数据，不生成虚构数字。
- 项目管理以搜索、筛选、项目身份、施工阶段、责任人、任务/进度、快捷操作为核心；按真实字段和权限展示。主次按钮明确，避免每行堆满等权操作按钮。
- 项目详情强调工程时间线、工序节点、记录与验收闭环；现有系统没有的数据/功能不得伪造标签页或操作入口。
- 操作体验：有意义的 hover/active/focus、明确成功/失败反馈、保存确认；反馈优先轻量 CSS 状态，禁止无意义的持续动画。
- 优先清晰列表、表格、分组标题和留白；避免满屏大卡片、重复图标、花哨照片、营销宣传区和装饰性进度条。
- 对客户信息和费用采用最小必要展示；遵守角色权限，不能为了预览暴露隐私或虚构收款进度。

## 4. 技术与性能：遵循真实项目，而非强制套模板
- 在修改或生成代码前，核实实际前后端架构、页面模板、依赖及版本。已读取的 0.17.6 ZIP 不自动等于线上 0.16.5；正式开发基线必须先核对。
- 如果现有前端是原生 JavaScript + CSS、后端 Node.js + SQLite，则优先在现有技术栈实现。TasteSkill 的 React/Next.js、Tailwind 或图标库属于可选工程建议，不得无依据迁移或强加依赖。
- 保留已有业务字段、权限、验证、操作流程、接口和数据库逻辑。允许视觉与信息布局大改，但不能借改版新增/删除业务能力；未授权不得更改线上服务、生产数据与接口契约。
- 低配置服务器优先：不增加不必要图片、字体包、动画库、重型组件、频繁请求；避免无意义的大量 DOM 与持续重绘。
- 不能把没有数据的界面呈现为已上线事实。设计稿统一用“【示意】”“【占位】”注明虚拟内容；优先以经脱敏的真实字段和业务结构呈现。

## 5. 正确的设计交付顺序（防止旧 UI 轻度换皮）
1. **读证据**：列出源码版本、页面/字段/角色/动作、当前截图、真实 Logo 或品牌资料；无法获取的明确标注未核实。
2. **先立视觉语言**：给出色板及每种颜色用途、字号/间距、导航、表格、按钮、状态、操作反馈规则。没有官方 Logo 不能谎称精确橙色已提取。
3. **同页重设**：先从“项目管理页”开始；只在旧页面与新设计同一业务、同一视口下比较。明确保留的业务骨架和重新构造的 UI。根据用户选择再做工作台首页。
4. **真实预览**：交付至少一张完整、可读的桌面高保真页面（默认 1440px 宽），不是微缩缩略图、泛化海报或纯文字方案。若无法生成实际预览，应明确告知并提供可执行替代物。
5. **对照验收**：逐项说明新旧页在品牌识别、可读性、搜索筛选、操作优先级、信息密度、响应反馈的改善及代价；未证实的功能不得算入改善。
6. **批准后开发**：设计评审通过后，在隔离环境按批准版本实现、核对真实功能、做回归与性能验证，最后再讨论发布。

## 6. 最低验收标准
- [ ] 使用真实 Logo / 可追溯品牌资源，浅色导航，品牌橙准确或明确标注暂定
- [ ] 页面明显不是旧 UI 换色，也没有变成深色工业控制台
- [ ] 主要功能、字段、角色权限、交互路径完整保留，未制造新业务事实
- [ ] 主按钮、搜索筛选、状态反馈、键盘焦点清晰；长时间阅读舒适
- [ ] 同页、同尺寸的新旧效果可直接比较，页面足够大可读
- [ ] 无高负载图片、强动效或未经核实的新框架依赖
- [ ] 未触碰生产服务器、数据库和线上业务数据
